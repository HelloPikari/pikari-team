# Production 500 hotfix, then making the single page belong to the theme

Covers 6 and 7 October 2026. The work came from a peer session (wordpress-plugins-10, in the monorepo) in four requests. Steve approved each merge and publish directly; the peer's word that he had approved was not enough.

## Decisions and why

- **1.0.3 hotfix: re-apply the old fix and add a guard so it can't happen again.** The cause was already known: the unanchored `--exclude='src'` in `release.yml` also stripped `vendor/*/src`. It was fixed in 7ef31a7, then reverted when #24 synced the generic template over it. Anchoring it alone would just wait for the next sync to undo it, so the build now fails if any Composer PSR-4 dir or classmap file is missing from the dist. Checked locally both ways: guard exits 1 with the old exclude, 0 with the new.
- **Loading card.css on the single page needed more than an enqueue (#48).** The peer's brief said card.css "looks safe" inside a theme. It wasn't: its first rule was a bare `*` margin/padding reset that would have flattened the whole site. The reset is now scoped. The standalone page keeps it at zero specificity via `:where(body.pikari-team-card-page)`. Inside a theme it applies at 0,1,0 via `:where(body:not(.pikari-team-card-page)) .pikari-team-card`, so theme element margins don't leak into the card. The WordPress-core review suggested zero specificity in both views; I rejected that because it lets theme `h2`/`p` margins into the card.
- **Filters behave the same in both views.** `pikari_team_card_css_file` returns a filesystem path, not a URL. So the default path is enqueued by URL, and a filtered path is inlined on a `false`-src handle, the same pattern core uses for `global-styles`.
- **Block themes get a registered block template, not a theme-detection hack (#49).** `register_block_template()` keeps the expected order: a theme's own `.html` beats Site Editor edits, which beat the plugin. Checked with stub templates on TT5 and TT1.
- **The template renders the card by extending the existing block, not adding one.** The card block gains `view: full` and `usesContext`. The context fallback is limited to the full view on a team member, so existing embed blocks with no member picked still render nothing.
- **The archive template was deleted, not fixed.** `has_archive` is false, so it could never render.
- **`<main>` stays in the classic template, without `id="main"`.** Themes disagree on who opens `<main>`. TT1 opens it in `header.php`; \_s, TT17, TT19 and TT20 expect the template to. A missing landmark is worse than a nested one, and a theme can override the template.
- **On the single page the card name is the h1.** The block template drops `post-title`, and TT1 prints the site title as a `<p>`, so the page had no h1. This uses Card_Renderer's existing `$context`: `single` gives h1, everything else (including `/card/`) gives h2.

## Surprises

- **The carousel QR had never been visible.** In the flex-centred slide, an SVG with no intrinsic width renders at 0×0. Nobody saw it because the single page never loaded CSS and `/card/` doesn't use the carousel.
- **Password-protected members leaked contact data.** The card printed phone, email and QR next to the password form. The classic path already did this; the new block path would have too. Found by the WordPress-core review.
- **The one screenshot difference was a timing artefact.** A `/card/` capture taken before the headshot loads gives a different hash. Wait for images before hashing; HTML diffs are the more reliable check.
- **My own git mistakes, both recovered:**
  - After a pre-commit hook failed, I ran `git checkout origin/main -- …` and overwrote my uncommitted work. lint-staged's backup stash had everything, and I verified a 0-line diff against it.
  - Later, `git stash push -- <file>` on a clean tree stashed nothing, so the `pop` that followed applied an older stash instead. Lesson: check that `git commit` exited 0 before touching the tree. Don't use stash push/pop as a temporary swap; copy files aside instead.
- **The named reviewer agents** (`wordpress-core-expert`, `accessibility-expert`) aren't available in these sessions, so I ran `general-purpose` agents briefed as those experts. Their findings were real: password leak, missing h1, embed fallback, standalone specificity.
